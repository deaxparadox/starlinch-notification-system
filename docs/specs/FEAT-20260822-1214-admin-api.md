# FEAT-20260822-1214 — Admin API

Branch: `main` (base: `main`)

## What's being built
The HTTP endpoints the admin panel (built in FEAT-20260822-1217) will call: list/create triggers,
upsert a template cell, toggle a cell on/off, test-send a cell, and view the notification log.
Locked down so only staff users can reach any of it.

## Current state (verified)
Read `backend/notifications/` before writing this spec: `models.py` has `Trigger`/`Template`/
`NotificationLog`/`PushSubscription` (FEAT-20260822-1213). `services.py` has `fire_trigger()` with
`override_recipient`/`override_channel` params already built specifically for this item's test-send
endpoint. `views.py`/`urls.py` are empty generator stubs — nothing to preserve there.
`config/urls.py` only wires `accounts.urls` so far. CORS (`CORS_ALLOWED_ORIGINS`,
`CORS_ALLOW_CREDENTIALS = True`) is already configured globally in FEAT-20260822-1212 — applies to
every path automatically, nothing new needed here despite this item's title mentioning it.

## Endpoints (all under `/api/admin/`, all require `IsAdminUser`)
- `GET/POST /api/admin/triggers/` — list (with nested `templates` — see serializer decision below),
  create a new `Trigger` row (`key`, `display_name`, `description`).
- `PATCH/DELETE /api/admin/triggers/<int:pk>/` — edit or remove a trigger row.
- `PATCH /api/admin/triggers/<int:trigger_id>/templates/<str:channel>/` — **upsert**
  (`get_or_create` then update — `unique_together = ("trigger", "channel")` means a plain `create()`
  raises `IntegrityError` on the second save to the same cell). Accepts whichever fields apply to
  the channel (`subject`/`body` for email/webpush; `wa_template_name`/`wa_language_code`/
  `wa_variable_mapping` for whatsapp).
- `PATCH /api/admin/triggers/<int:trigger_id>/templates/<str:channel>/toggle/` — body `{"is_active": bool}`.
  Kept separate from the upsert PATCH so the on/off switch in the UI can flip state without also
  resubmitting (and risking accidentally blanking) the template content.
- `POST /api/admin/triggers/<int:trigger_id>/templates/<str:channel>/test-send/` — body
  `{"recipient": "..."}`. Calls `fire_trigger(trigger.key, user=None, context={}, is_test=True, override_recipient=recipient, override_channel=channel)`.
- `GET /api/admin/logs/?trigger=<key>&channel=<channel>&status=<status>` — read-only, filtered
  `NotificationLog` list, newest first.

## Design rationale
- **`IsAdminUser`** (DRF's built-in, checks `request.user.is_staff`) as `permission_classes` on
  every view in this item — the real, backend-enforced boundary per ADR-0001's auth design. No
  frontend check is a substitute for this.
- **Serializer decision**: `GET /api/admin/triggers/` always returns all 3 channel keys
  (`whatsapp`/`email`/`webpush`) per trigger, `null` for any channel with no `Template` row yet —
  not just the rows that happen to exist. Keeps "fill the gaps" logic in one place (the Django
  serializer) instead of duplicated in the frontend table-rendering code.
- **Upsert, not create**: the PATCH-to-a-channel-cell endpoint uses `get_or_create` then updates the
  fetched/created instance's fields — required because of `unique_together`, and matches how the
  admin UI actually works (there's no separate "does this cell already have a template" check on
  the frontend; it just PATCHes).
- **Test-send reuses `fire_trigger()`** rather than a separate code path, via the
  `override_recipient`/`override_channel` params already built for exactly this in
  FEAT-20260822-1213 — one send implementation, not two.
