# FEAT-20260822-2251 — Logs page

Branch: `feature/ui-redesign` (base: `main`)

## What's being built
`/admin/logs` — the page the sidebar's "Logs" link has pointed at since FEAT-20260822-2249 without
a page to land on. Uses `GET /api/admin/logs/` (built in FEAT-20260822-1214, never had a UI).

## Current state (verified)
Backend: `GET /api/admin/logs/?trigger=<key>&channel=<channel>&status=<status>`, all filters
optional, returns `NotificationLogSerializer` rows (`id`, `trigger_key`, `channel`, `recipient`,
`status`, `provider_response`, `error`, `is_test`, `created_at`), newest first, **unpaginated** (no
`DEFAULT_PAGINATION_CLASS` set in `REST_FRAMEWORK` settings) — fine for this app's actual data
volume, no pagination added here (YAGNI).

## Gap found while designing this page
No `Select` component exists in the FEAT-20260822-2248 library — every filter on this page needs
one. This is the same "same pattern, other locations" case Module 6 calls out: rather than a one-off
styled `<select>` on just this page, add `components/ui/select.tsx` reusing the exact field styling
already factored out in `input.tsx` (`fieldBase`) so it's visually identical to every other input
and available for any future filter UI, not just this one.

## Page contents
- Filter row: `Select` for trigger (populated from `GET /api/admin/triggers/`, "All triggers" +
  each trigger's `display_name`/`key`), `Select` for channel ("All channels" +
  whatsapp/email/webpush), `Select` for status ("All" / Sent / Failed). Changing any filter refetches
  via updated query params.
- `Table`: Time (relative-ish or locale timestamp), Trigger, Channel (`ChannelBadge`), Recipient,
  Status (`StatusBadge`), Test (small muted "test" tag when `is_test`), Error (truncated text,
  full text in a `title` attribute for hover — not worth a full expand/dialog interaction for a
  short error string).
- `EmptyState` when no logs match the current filters (distinguishes "no logs at all yet" vs.
  "no logs match these filters" only by button action: the former links to `/admin`, the latter has
  no action — it's just "try different filters").
- `Skeleton` rows while loading.

## Design rationale
No new architecture decisions — reuses `authFetch`, the existing `Trigger`/`NotificationLog` types
already in `lib/types.ts`, and every component from FEAT-20260822-2248 plus the one gap-filling
`Select` addition.

## Verification plan
Seed a few `NotificationLog` rows (mix of sent/failed/test) via the admin panel's test-send (already
exercised in FEAT-20260822-2250's verification), load `/admin/logs`, confirm rows render correctly,
each filter actually narrows the result set (checked against the real backend query params, not
just UI state), and the empty state shows correctly with a filter combination that matches nothing.
